## 1. Scientific objective

V1.3C tests whether NAAIL's governed multi-agent architecture produces measurably different professional forensic-accounting outputs than simpler AI/workflow architectures when all conditions receive the same case evidence and task contract.

The primary benchmark is the existing Chapter 2–15 case suite developed for the forensic-accounting / POMELO book. The benchmark therefore builds on already-developed professional case material instead of generating new cases merely to obtain validation results.

### Primary research question

**Does a governed multi-agent architecture improve evidence-grounded forensic-accounting judgment relative to deterministic, single-agent, and sequential-agent architectures across an expert-reviewed suite of real-case-derived XYZ Digital Twins?**

No positive architecture effect is assumed. Null, negative, contradictory and failed results must be retained.

## 3. Case provenance and XYZ rule

The benchmark must distinguish three evidence classes:

1. **Real historical evidence** — rights-cleared/public source evidence and documented facts.
2. **XYZ Digital Twin evidence** — transformed/anonymized/simulation case material derived from the teaching-case design.
3. **Synthetic or counterfactual evidence** — generated values, perturbations, alternative scenarios or falsification cases.

These classes must never be silently mixed. Every benchmark artifact and Evidence Passport™ must identify its evidence class and provenance.

The public/student-facing benchmark may use **XYZ** identities where required by the book design, permissions, pedagogy, confidentiality or experimental blinding. Protected real-case crosswalks must remain outside public GitHub when disclosure is not authorized or would weaken experimental integrity.

## 5. Leakage firewall

The architecture under test must not receive the protected instructor solution, real-case identity crosswalk, Human Gate score, hidden rationale, answer key or post-outcome annotations.

Separate repositories/storage boundaries should be used for:

- **PUBLIC/TEST INPUT:** permitted XYZ case packet and task contract.
- **PRIVATE GOLD VAULT:** instructor solution, expert rationale, scoring key, crosswalk, hidden labels.
- **RUN OUTPUT:** immutable model/agent output and run manifest.
- **EVALUATION:** blinded scoring and machine-computable metrics.

Any leakage invalidates the affected run and must be recorded as a failed experiment, not silently rerun and replaced.

---

## 6. Four architecture conditions

Every eligible chapter should be executed under the same evidence/task contract using four prespecified conditions:

### A0 — Deterministic workflow
Rule-based / fixed analytical workflow with no autonomous agent deliberation beyond the specified deterministic pipeline.

### A1 — Single agent
One model/agent receives the permitted evidence and completes the professional task without multi-agent decomposition.

### A2 — Sequential agents
Specialist steps operate sequentially, passing outputs forward under a fixed orchestration protocol.

### A3 — Governed NAAIL multi-agent
NAAIL's governed architecture may use specialist agents, critic/defender or adversarial review, evidence checks, verification and decision governance, subject to the same underlying evidence and task boundary.

The experiment tests the architecture, not unequal access to evidence.

## 9. Professional Decision DAG™

The benchmark should capture the reasoning structure as inspectable professional decision nodes rather than score only a final answer.

Minimum node families:

**Evidence → red flag / anomaly → assertion or professional issue → alternative explanation → procedure/test → finding → uncertainty → professional judgment → recommended action.**

This permits evaluation of *why* an architecture reached a conclusion and whether unsupported conclusions were generated.

## 10. Evaluation dimensions

V1.3C should evaluate architecture effects across at least:

### Professional quality
- correct issue/red-flag identification;
- accounting/auditing/forensic judgment quality;
- procedure appropriateness;
- treatment of alternative explanations;
- conclusion quality;
- uncertainty calibration.

### Evidence quality
- evidence grounding;
- citation/provenance correctness;
- unsupported-claim rate;
- evidence coverage;
- Evidence Passport completeness.

### Scientific reliability
- reproducibility;
- run-to-run stability;
- failure rate;
- contradiction rate;
- sensitivity to perturbation;
- out-of-sample/generalization performance;
- independent-replication result.

### Operational performance
- latency;
- token/computational use;
- total run cost;
- cost per professionally verified output;
- Human Gate pass rate.

External model benchmarks must remain clearly separated from **NAAIL-specific professional validation metrics**.

## 11. Blind scoring

Where feasible, expert evaluators should receive outputs with architecture identity hidden. Scoring should occur against the pre-frozen rubric rather than after observing which architecture generated the answer.

The benchmark must retain disagreement between expert raters. Agreement statistics and adjudication rules should be prespecified.

A useful outcome structure is:

```text
Case × Architecture × Run × Evaluator × Metric
```

This supports within-case comparisons while controlling for case difficulty.

---

## 12. Falsification and adversarial tests

V1.3C should actively attempt to falsify claims of architecture superiority.

Required challenges should include, where suitable:

- removal of nonessential evidence;
- conflicting evidence;
- plausible distractors;
- missing evidence;
- alternative explanations;
- temporal holdouts;
- evidence-order perturbation;
- model/runtime substitution;
- repeated runs;
- case-level leave-one-out analysis;
- cross-chapter transfer tests.

A3 is scientifically valuable even if it does **not** outperform simpler conditions. Null and negative results define where governance complexity is or is not justified.

## 15. Relationship to the frozen two-core architecture

This benchmark does **not** add a third core.

- **Stable Knowledge Core™:** forensic accounting, accounting/auditing theory, professional standards, case logic, professional judgment, scientific design and falsification.
- **Replaceable Technology Core™:** models, agents, orchestration, RAG/GraphRAG/KAG, code, evaluators, runtime, tools and infrastructure.

The Chapters 2–15 XYZ suite is a **benchmark/evidence layer**, not a new core.
