## Professional repository baseline

Future NAAIL products should follow the standard defined in `NAAIL_PRODUCT_STANDARD.md`. At minimum, a serious product repository should expose:

- clear project identity and research status;
- README with purpose, architecture, quick start, evidence/governance, evaluation, maturity boundary, citation and independence statement;
- `CITATION.cff`;
- `ROADMAP.md`;
- `SECURITY.md`;
- `CONTRIBUTING.md` where collaboration is appropriate;
- explicit license / IP boundary;
- third-party provenance and non-affiliation language;
- reproducibility and evaluation documentation proportionate to project maturity.

## Scientific and governance rule

For major NAAIL studies and product claims, preserve the sequence:

**literature validation → competing hypotheses → executable empirical design → real data / code → adversarial review → robustness → falsification → replication → Chain-of-Evidence / provenance → human approval.**

Agent consensus, model confidence, statistical significance, benchmark score, or predictive accuracy alone is not sufficient for a scientific or professional claim.

## Licensing and IP boundary

- Public GitHub documentation is not a patent filing.
- Patent-sensitive implementation details should remain private until reviewed.
- Third-party code, models, datasets, standards, trademarks, and forks retain their own licenses and rights.
- Existing MIT/Apache/open-source grants cannot simply be revoked for copies already distributed under those terms.
- Prefer a **public research specification + private implementation/core** structure when commercial/IP protection matters.
